# 認証・認可設計（ローカル開発環境）

## 目的と対象範囲

このサンプル EC サイトに、ZITADEL を用いた認証・認可を導入する。対象は Storefront と Admin の両方であり、`docker compose up` でローカル環境を再現できることを目標とする。

これはローカル開発用の構成である。公開環境向けの TLS、独自ドメイン、メール配送、MFA、ソーシャルログインは今回の対象外とする。

## 全体構成

- ZITADEL は Docker Compose で自己ホストする。
- Storefront と Admin は同一の ZITADEL ユーザーディレクトリを共有するが、OIDC アプリケーションは別々に登録する。
- 両フロントエンドは Authorization Code Flow with PKCE を使用する React SPA とする。
- 各 API は受け取った Bearer JWT を ZITADEL の公開鍵で検証する。検証対象は署名、issuer、audience、期限、ロールである。
- アプリ専用の BFF や、アプリ側のログインセッションは追加しない。

別アプリにしても、ZITADEL の SSO セッションは共通である。ブラウザですでに ZITADEL へログイン済みなら、もう一方のアプリでは通常、認証情報の再入力は不要になる。

## ユーザーとロール

ロールは以下の 2 種類とする。

| ロール | 権限 |
| --- | --- |
| `customer` | ログイン後に注文を作成し、自分の注文だけを閲覧・キャンセルできる。 |
| `admin` | Admin 画面および商品・在庫・画像に関する管理 API を操作できる。注文データにはアクセスできない。 |

- 自己登録は許可しない。利用者は初期化で作成するローカル開発用アカウントを使用する。
- `admin` は初期作成する EC 管理者にだけ付与する。
- EC 管理者と ZITADEL 自体の運用管理者は分離する。ZITADEL の運用管理者は、通常の EC 操作や動作確認に使用しない。
- アプリ側にユーザー情報テーブルは作らない。注文の `customer_id` には、ZITADEL の不変ユーザー ID（JWT の `sub`）を保存する。表示名、メールアドレス、ロールはトークンのクレームから得る。

## 初期化と開発用アカウント

Compose 起動後、ZITADEL が利用可能になってから初期化処理を一度実行する。

1. ZITADEL の組織、ロール、OIDC アプリケーションを設定する。
2. 購入者 2 名と EC 管理者 1 名を作成する。
3. 購入者には `customer`、EC 管理者には `admin` を付与する。
4. k6 専用のサービスアカウントを作成し、管理 API に必要な権限を付与する。

初期化は冪等にする。すでに存在する組織、アプリケーション、アカウント、ロールは再作成しない。初期注文データは作成しない。

初期アカウントはローカル専用の固定テスト認証情報とし、Storefront と Admin のログイン前画面、および README に明記する。実際の値、ZITADEL の暗号鍵、初期化用認証情報、k6 サービスアカウントのクライアントシークレットは Git 管理外の `.env` に置く。リポジトリには `.env.example` を置く。

既存の無認証注文は所有者を安全に対応付けられないため、認証導入時はローカル Compose ボリュームを再作成して破棄する。

## Storefront の動作

- 商品と在庫の閲覧は未ログインでも可能とする。既存どおり、在庫数も公開する。
- 注文作成、注文履歴、注文詳細、注文キャンセルはログイン必須とする。
- 未ログインで保護された画面や操作に到達した場合は、元の URL を保存して ZITADEL のログイン画面へ遷移する。認証後は元の画面へ戻す。
- アカウント画面では表示名、メールアドレス、ログイン状態、ログアウトを表示する。プロフィール編集とパスワード変更は ZITADEL のアカウント管理に委ねる。
- トークンは `sessionStorage` にのみ保持し、同じタブの再読み込みではログイン状態を維持する。ブラウザまたはタブを閉じれば状態は消える。`localStorage` には保存しない。
- ログアウト時はアプリ内トークンを破棄するだけでなく、ZITADEL の SSO セッションも終了する。
- パスワード再設定はローカル環境では提供しない。必要時は ZITADEL 運用管理者が再設定する。

## Admin の動作

- Admin はログイン必須とする。
- `admin` ロールを持たないユーザーが Admin の画面または API を利用しようとした場合、アクセスを拒否する。
- ログイン前画面には、ローカル開発用テスト認証情報を表示する。

## API の認可境界

| API の種類 | 認証・認可 |
| --- | --- |
| `GET /products`、`GET /products/:id` | 公開 |
| `GET /inventories`、`GET /inventories/:id` | 公開 |
| `POST /orders` | ログイン必須。注文者はトークンの `sub` とし、クライアントからの `customer_id` は受け取らない。 |
| `GET /orders` | ログイン必須。トークンの `sub` に一致する注文だけを返す。 |
| `GET /orders/:id`、`POST /orders/:id/cancel` | ログイン必須。対象注文の `customer_id` がトークンの `sub` と一致するときだけ許可する。 |
| `/admin/*` | `admin` ロール必須。 |

`POST /inventories/:id/reserve` と `POST /inventories/:id/restock` は外部 API として廃止する。予約は Order Service から Kafka を介して実行し、在庫補充は `admin` 必須の `POST /admin/inventories/:id/adjust` に一本化する。

## k6

k6 は人間用管理者のパスワードを使用しない。初期化で作成するサービスアカウントが Client Credentials Flow で短命トークンを取得し、在庫補充を管理 API 経由で行う。クライアントシークレットは `.env` でのみ渡す。

## エラー表示と観測

- API から `401 Unauthorized` を受け取った場合、フラッシュメッセージでセッション切れを伝え、ログインへ遷移する。認証後は元の画面へ戻す。
- `403 Forbidden` を受け取った場合は再ログインさせず、画面上のフラッシュメッセージで必要な権限がないことを伝える。
- JWT、パスワード、メールアドレス、ZITADEL のユーザー ID（`sub`）はログ、トレース、メトリクスに記録しない。認可拒否では HTTP ステータス、対象 API、不足権限だけを記録する。

## テストとドキュメント

- 既存の MSW を使う単体テスト・フロントエンド E2E テストは維持し、認証状態をモックできるようにする。
- 実 ZITADEL と Compose を使う統合 E2E を別コマンドで追加する。購入者のログインと自分の注文だけへのアクセス、購入者による管理 API の拒否、管理者による管理 API の操作を検証する。
